## Plan the setup

Only add devices you own, or devices whose owner and users have agreed to it. The page shows when each device was on and how busy it was, so monitoring a device someone else uses needs their knowledge and, where the law requires it, their consent; see [Intended use](../README.md#intended-use).

| Device | Install | Role |
| --- | --- | --- |
| Raspberry Pi or other always-on Linux machine | Docker image, or the Linux archive with a systemd service | **hub**: shows every device and keeps all history |
| Windows PC (x64 or ARM) | MSI installer | data only: reports to the hub |
| Other Linux machine | Docker with `DATA_ONLY=true`, or the Linux archive | data only, or with its own page |
| macOS | [from source](#run-from-source) | not packaged yet |

All devices must be on the same local network as the hub. They need no internet access, except the hub for its once-a-day version check, which can be turned off. How they talk to each other is in [How it works](architecture.md).

den-watcher listens on port **9393** by default.

## 1. Set up the hub with Docker

On the Pi, with Docker and the Compose plugin installed, get `compose.yaml` and `.env.example` from this repository (a `git clone` is the easiest), then:

```bash
cp .env.example .env   # optional, to change settings
docker compose pull
docker compose up -d
```

This runs the published image `ghcr.io/programmer-den/den-watcher` for arm64 and amd64; the Pi builds nothing. Open `http://<the Pi's address>:9393` from a phone or PC on the same network.

What `compose.yaml` sets up:

- the host's `/proc` and `/sys` mounted read-only, so the container measures the Pi, not itself
- `/etc/localtime` mounted read-only, so the page shows the Pi's time zone, and `/etc/os-release` at `/host/etc/os-release` (`HOST_ETC` points to `/host/etc`), so the System card names the Pi's system instead of leaving it out
- a `data` volume for the [database](database.md), kept across updates
- a read-only container running as a non-root user, with every capability dropped and `no-new-privileges`
- the port published over IPv4 only, so the program sees each client's real address. A browser that tries IPv6 first falls back to IPv4 by itself

`IMAGE_TAG` in `.env` picks the version: `latest` (default) is the newest release, a release such as `0.1.0` stays on it, and `main` follows every change on the main branch, for testing. `docker compose up -d --build` builds the image from the checkout instead.

### Show more disks

By default the page shows the disk Docker keeps its data on, usually the system disk. The container sees no other host folder unless it is mounted. To show a USB disk mounted at `/mnt/usb`, mount it read-only at the same path in `compose.yaml` and list it in `.env`:

```yaml
    volumes:
      - /mnt/usb:/mnt/usb:ro
```

```bash
DISK_PATHS=/,/mnt/usb
```

den-watcher refuses to start when a path in `DISK_PATHS` cannot be read, and says which one. A path that does not answer within 2 seconds, such as a network share whose server is away, is left out of the readings until it answers again (and for 30 seconds after a late answer), and the log says so once; the rest of the page goes on.

### Open the page by name

The page answers when opened by an IP address, `localhost`, the machine's hostname or any `.local` name, such as `http://raspberrypi.local:9393`. Inside Docker the hostname is the container's, so a bare `http://raspberrypi:9393` or a name from the router's DNS has to be listed:

```bash
ALLOWED_HOSTS=raspberrypi,pi.fritz.box
```

Other names are refused with `421 Misdirected Request` ([why](architecture.md#local-network-only)). List the names alone, with a port at most: an entry such as `http://pi.lan` is left out, and the log warns about it by name.

### Install the page as an app

The page can be put on the home screen of a phone or tablet, with its name and the bear as the icon: *Add to Home screen* in Chrome's menu on Android, *Share › Add to Home Screen* in Safari on iOS. It then opens in a window of its own, without the browser's address bar. This works over plain http on the local network. Open it by a name or address that stays the same, as the icon keeps the address it was added with.

Opened over https, such as behind a reverse proxy with a certificate the browser trusts, or on `localhost`, the page is a full Progressive Web App: its service worker (`sw.js`) starts, Chrome and Edge offer to install it, on a PC too, and the header gets an install button (an arrow into a tray) while the browser offers that. The service worker keeps the page's files from the first visit on, a new version's as soon as the hub has it, so the installed app opens the page while the hub cannot be reached, also when the reverse proxy answers for it with an error such as 502, says that the hub is not answering, and catches up once it answers again; the values themselves are never kept offline. Browsers start a service worker only for such a page, so over plain http at the device's address the page has none and no install button. To try it over http, list the page's address in Chrome under `chrome://flags/#unsafely-treat-insecure-origin-as-secure`.

### Show the page on a wall display

Add `?kiosk` to the page's address, such as `http://raspberrypi.local:9393/?kiosk`, for a screen on the wall: the page leaves out the list of devices and every button for arranging the cards, picking the range, the language or the theme, shows its text larger, always shows the cards, also where that browser was switched to the timeline, and shows the alerts of every device above them, each with its device's name. On a hub it shows each device in turn for 30 seconds, those with an alert or that do not answer first; a PC or laptop that is switched off is skipped. `?kiosk=60` shows each for 60 seconds (10 at least, a day at most). The page takes no clicks or keys then, so nothing on it changes by accident; it follows the screen's light or dark mode, and shows the language last picked in that browser, or else the browser's own. Open it in the browser's own full-screen or kiosk mode, such as `chromium --kiosk "http://raspberrypi.local:9393/?kiosk"`. The demo shows it too, with `?kiosk` added to its address.

## Or: set up a Linux machine without Docker

Every [release](https://github.com/Programmer-Den/den-watcher/releases) after 0.1.0 has an archive for Linux: `den-watcher-<version>-linux-arm64.tar.gz` for a Raspberry Pi with a 64-bit system, `-linux-amd64.tar.gz` for a PC. It holds the program, a systemd service and an install script:

```bash
tar -xzf den-watcher-<version>-linux-arm64.tar.gz
cd den-watcher-<version>-linux-arm64
sudo ./install.sh
```

The service starts right away and at every boot, on port 9393. Settings go in `/etc/den-watcher.env`, followed by `sudo systemctl restart den-watcher`. The history is kept in `/var/lib/den-watcher`. Running natively, it sees every disk and needs no mounts. Like the container, the service runs as an unprivileged throwaway user that can write only its own folder.

To update, unpack the newer archive and run its `install.sh` again; settings and history are kept. `sudo ./install.sh --uninstall` removes it, and `--uninstall --purge` also deletes its settings (with any made with `systemctl edit`) and history.

### Add-ons

Add-ons are optional programs that collect more data than den-watcher itself does. Each one runs as a program of its own, so a device only runs the ones picked for it: on Linux each as a service or container, on Windows as a child process of the Den-Watcher service. They come in two editions. **Cub** is den-watcher with the lightweight add-ons, kernel, memory, pressure, Wi-Fi and inodes, which read a few small files or counters at each poll. **Grizzly** is Cub with any of the other add-ons, which cost more or need more rights. In a terminal, `install.sh` first asks for the edition, listing what Cub tracks. Cub then installs without further questions; Grizzly asks which data you want to collect, group by group, starting with Cub's add-ons picked (on an update, those installed before): for each group whether to track it, then for each of its add-ons whether to install it, and for the Wi-Fi and Bluetooth add-ons what they collect (`WIFI_NEARBY` and `BLUETOOTH_NAMES`, written to `/etc/den-watcher.env`). `--addons=cub` installs Cub without asking, `--addons=cub,power` Grizzly with the power add-on, `--addons=power` only the add-ons named, `--addons=cub,network` Cub with every add-on of a group, `--addons=` none, and an update without the option and without a terminal keeps the add-ons installed before.

The groups are the same in every installer, in Docker's profiles and in the Android app. CPU, memory, disks, network traffic, temperatures, graphics cards, battery and fans are always collected; each group adds:

| Group | Name in `--addons` and `COMPOSE_PROFILES` | Add-ons | What else can be chosen |
| --- | --- | --- | --- |
| System details | `details` | `kernel`, `memory`, `pressure`, `inodes` | |
| Hardware | `hardware` | `power`, `gpu`, `smart` | |
| Network | `network` | `wifi`, `ports` | `WIFI_NEARBY`: the Wi-Fi networks nearby, or only the connected one's quality; on Windows also `WIFI_SCAN` |
| Bluetooth | `bluetooth` | `bluetooth` | `BLUETOOTH_NAMES`: the devices' names, or only their kinds |
| Processes and containers | `programs` | `processes`, `containers` | |

| Add-on | What it adds |
| --- | --- |
| `power` | the power the machine draws, with its history: a Raspberry Pi 5 in total (through `vcgencmd`), Intel and AMD CPUs per package and memory (RAPL), sensors the kernel lists under hwmon (such as AMD GPUs) and NVIDIA GPUs (through `nvidia-smi`). `nvidia-smi` is asked every 30 seconds and `vcgencmd` every 10, since starting a program costs more than the file reads of the rest; in between, their last answer is shown. A call of `nvidia-smi` that has not ended after 5 seconds, as when the driver hangs, is given up on: no NVIDIA GPU is shown and none is started until it ends. `vcgencmd` only asks the firmware and answers at once, so the Pi 5's minute averages catch short spikes too. On Windows: the energy meters Windows offers (RAPL and laptop meters), the battery while the PC runs on it, and NVIDIA GPUs. On Linux it runs as root, since newer kernels let only root read the CPU's energy counters, but without any capability or network access |
| `gpu` | more about NVIDIA graphics cards than the page shows, from one `nvidia-smi` call every 30 seconds: the fan, the graphics and memory clocks and the use of the video encoder and decoder, with their history, and the performance state and power limit, without. Without `nvidia-smi` it reports nothing, and while a call of it has not ended after 5 seconds, as when the driver hangs, it reports nothing and starts no other. With several NVIDIA GPUs, this add-on and the power add-on keep each card's history under the first 8 digits of its UUID, since `nvidia-smi` may number the cards differently after a boot; a machine's only GPU keeps its number 0. On machines with several NVIDIA GPUs, their history therefore starts under new names once after the update. Likewise, adding a second card or removing one so that one is left moves the history of the remaining card to a new name once. With the Linux archive it runs as root, since the add-ons there share a folder only root writes, but without any capability or network access; on Windows it runs in the service's Local Service account |
| `inodes` | Linux only: how many inodes (files and folders) each real mounted filesystem has in use, in percent with its history, by mount point. A disk full of small files can run out of inodes while it still has free space, and then no new file fits. Memory and kernel filesystems, network shares (whose server may not answer), read-only images and filesystems without a fixed number of inodes, such as btrfs and vfat, are left out, as is what is mounted below the folders of Docker (`/var/lib/docker`, or `DOCKER_DIR` in `/etc/den-watcher.env`), containerd (also the containerd of k3s and RKE2 in `/var/lib/rancher/{k3s,rke2}/agent/containerd`, of MicroK8s in `/var/snap/microk8s/common/var/lib/containerd` and of k0s in `/var/lib/k0s/containerd`), Podman (also rootless Podman's `~/.local/share/containers/storage`), LXD and Incus (such as one ZFS dataset per container layer), which would come and go with the containers; a disk mounted below the folders of Docker, containerd or Podman, such as one for Docker's volumes, is kept, and of an LXD or Incus storage pool only the pool itself, not each container's volume. Below some folders nothing is reported, not even a disk, as each mount there belongs to one container or pod: LXD's and Incus's `devices` folders (where an instance's disks, such as a custom volume, are mounted again), `rootfs` in Docker's folder and `tmpmounts` in each of those containerd folders (containerd's snapshots, such as one device-mapper disk per container), the folders of containerd's running containers (`/run/containerd/io.containerd.runtime.v2.task`, `/run/k3s/containerd/io.containerd.runtime.v2.task` with k3s and RKE2, `/var/snap/microk8s/common/run/containerd/io.containerd.runtime.v2.task` with MicroK8s and `/run/k0s/containerd/io.containerd.runtime.v2.task` with k0s), and kubelet's `pods` and `plugins` in `/var/lib/kubelet` (also with k3s and RKE2), `/var/snap/microk8s/common/var/lib/kubelet` (MicroK8s) and `/var/lib/k0s/kubelet` (k0s), so a Kubernetes volume, such as one of Longhorn or another CSI driver, does not show; the disk that holds such volumes shows where it is mounted elsewhere. Only these default folders are covered: with k3s, RKE2 or k0s set up with a data folder of their own (`--data-dir`), or rootless k3s, which keeps its data in the user's home, their containers' mounts still show. A device mounted at several paths shows once, at the first of them that answers. Where filesystems are mounted over each other at one path, the top one, which hides the others, is the one reported, and a filesystem hidden by one mounted later on a folder above it is left out. It runs as root, since the add-ons of the Linux archive share a folder only root writes, without any capability or network access |
| `pressure` | how much of the time tasks had to wait for the CPU, for memory and for disks and other I/O, with its history (Linux pressure stall information from `/proc/pressure`; *tasks waiting* is the share of the last ten seconds in which at least one task waited, *all tasks stalled* the share in which no task could run). Kernels without PSI, or with it switched off, report nothing: Raspberry Pi OS switches it off, so there add `psi=1`, after a space, to the end of the one line in `/boot/firmware/cmdline.txt` and restart the Pi. Reading needs no privileges: with the Linux archive it runs as root, without any capability or network access, only to write to the shared add-on folder, and its container runs as the image's user. On Windows, which measures no such waiting, it reports the closest signals its performance counters offer instead, under names of their own: *CPU: threads waiting* (threads ready to run that wait for a processor, at the moment of the reading), *Memory: pages read from disk* (per second, for hard page faults, each of which makes a program wait for memory that was paged out or for a mapped file) and *Disks: busy* (the share of time the disks had work, averaged over all disks). These are approximations: they show that something queues, not for how long anything stalled, so they cannot be compared with the Linux percentages |
| `kernel` | what the kernel is busy with, with its history: context switches, interrupts and new processes and threads per second (`/proc/stat`, which counts each new thread as a process too), open files (`/proc/sys/fs/file-nr`), sockets in use (`/proc/net/sockstat`), established TCP connections and TCP retransmissions per second (`/proc/net/snmp`). It reads the host's network values through `/proc/1/net`, since `/proc/net` shows only the network of the program that reads it. With the Linux archive it runs as root only to write to the add-on folder, without any capability or network access; its container runs as the image's user. On Windows it reads the closest values Windows offers: context switches and interrupts per second (performance counters), open handles instead of open files (`GetPerformanceInfo`; handles are files and every other kernel object), established TCP connections and TCP retransmissions per second, both over IPv4 and IPv6 as on Linux (`GetTcpStatisticsEx`). Windows counts no new processes and no sockets in use, so those are missing there. The values are shown in four groups of similar size, each with its own charts: context switches and interrupts; new processes; open files or handles and sockets; TCP |
| `wifi` | the link quality (in percent, with its history) and signal (in dBm, only its current value, as it is below the 0 the charts start at) of each connected Wi-Fi interface; interfaces that are not connected report nothing. On Linux it reads `/proc/net/wireless`, where the quality is the driver's link quality; Wi-Fi 7 adapters (such as the Intel BE200) report nothing there, as the kernel keeps that file only for older Wi-Fi, so they show nothing. From Linux 6.4 on, reading it makes the kernel log once per boot that the add-on uses "wireless extensions", whatever the adapter; that is expected. The file it reads is readable by anyone: with the Linux archive it runs as root only to write to the shared add-on folder, without any capability or network access, and its container runs as the image's user. On Windows it asks Windows' own WLAN API (`wlanapi.dll`) and names each interface by its adapter's description, cut short where it is too long for a label (keeping the " #2" Windows adds to a second adapter of the same model); it keeps the values by the adapter's interface GUID, so two adapters of the same model stay apart. Its quality is Windows' signal quality (0 % at -100 dBm, 100 % at -50 dBm), so the two systems rate the same signal a little differently. If Windows withholds the current connection (Windows 11 24H2 and later do so from programs without location access), the quality is worked out from the signal by that same rule. On a Windows without the WLAN AutoConfig service or a Wi-Fi adapter, such as most servers, it reports nothing. The link's bitrate is left out, as Linux reports it only through netlink. It also lists the **Wi-Fi networks nearby** in a card of their own, from the scans the system makes on its own, and on Windows from one it asks for every 5 minutes on each connected interface (unless the installer option `WIFI_SCAN=0` turns that off), as Windows hardly scans while connected and would soon list only the access point it is connected to (such a scan takes the Wi-Fi to other channels for a moment, which can add a short delay; Linux gets no such scan, as NetworkManager leaves it to polkit, which usually refuses the add-on's user): how many networks are in range (with its history), how many hidden ones, the network it is connected to, and for each of the 15 strongest networks by name its signal in percent (with its history, so the chart shows when the network was in range and how strong), its channel with band and width (and the other bands its access points use), its security (open, WEP, WPA, WPA2, WPA3, Enterprise or OWE), and where known its signal in dBm, Wi-Fi generation, fastest rate and number of access points. Access points the system last saw more than 15 minutes ago are left out. As the system scans only every few minutes, the add-on asks for them every 30 seconds, not with every reading. On Linux it asks NetworkManager over the system D-Bus (as on Raspberry Pi OS bookworm and later), which gives the signal in percent, the fastest rate and, from NetworkManager 1.46, the width, but neither dBm nor the generation; without NetworkManager, as on Raspberry Pi OS bullseye, the card is left out. On Windows it reads the list the WLAN API keeps (`WlanGetNetworkBssList`), with the signal in dBm and the security, generation and width from the access points' beacons; Windows 11 24H2 and later give it only with location access, as for the current connection, and leave the card out otherwise. Hidden networks are only counted, and access points' hardware addresses are never shown. It also reports each access point on its own, under a hash of its hardware address, which a hub keeps by hour for each of its devices (`GET /api/wifi`), so it can compare which networks its devices see and how strong: *Compare devices* shows, under *Wi-Fi nearby*, which device hears which network (*Who sees what*), and how well each device hears the network they are connected to, through which of its routers, with each router's radios counted as one access point (*Home network*), how many routers send on each channel, with the least crowded one for the home network (on 2.4 GHz one of 1, 6 and 11, on 5 GHz the 80 MHz block with the fewest) (*Channels*), and how alike the devices hear the networks, as two devices in one room hear the same routers about as strong, with the ones probably together and when each device was somewhere else than it is now (*Where devices are*), where each device was over the last day, hour by hour: at a place named on the page, such as Work or the kitchen, which a device is counted at when it hears the networks there at least 80 % alike, or else at home near the router of the home network it heard best, named after the device the router is where the hub shows it as one; *Name this place* names the spot a device is at by what it hears now, and the phone app keeps what it hears while away from the hub and sends it once back (*Places*), and what changed over the last day: networks that appeared or went, a router of the home network that moved to another channel, a new access point of it, and a network named like it but secured otherwise, which may be a copy set up to catch passwords and is a [warning](data.md#alerts) too (*Changes*) |
| `memory` | memory details beyond used, cached and swap, with their history. On Linux, from `/proc/meminfo` and `/proc/vmstat`: dirty memory and memory being written back, the kernel's slab caches, shared memory, page tables and committed memory in bytes, page faults and major page faults (read from disk) per second, and swapping in and out in bytes per second. Reading needs no privilege: with the Linux archive it runs as root only because the add-on folder is root's, without any capability or network access, and its container runs as the image's user. On Windows, from the Memory performance counters, the nearest Windows has: modified memory (waiting to be written), the kernel's paged and nonpaged pools in place of the slab caches, committed memory, page faults per second, disk reads for page faults per second in place of major page faults (one read can bring in several pages), and paging in and out in bytes per second, which counts the page file and memory-mapped files, not only swapping. Windows has no counter for memory being written back, shared memory or page tables, so those are left out. The values are shown in five groups of similar size, each with its own charts: the kernel's memory (slab caches or pools, shared memory, page tables); committed memory; memory waiting to be written; page faults; and what goes to and from disk (major page faults or disk reads for them, swapping or paging) |
| `ports` | the TCP and UDP ports the machine listens on, each with the addresses it listens on (`0.0.0.0` and `::` for all; a long list shows as many whole addresses as fit in 80 characters and ends in "+N" for the rest), live only, and how many there are, with its history. UDP ports in the range the system hands out to programs that only send (on Linux the host's `ip_local_port_range`, 32768 to 60999 by default; its container has a network of its own and so sees only that default, not a range changed on the host; 49152 to 65535 on Windows) are left out, as browsers and DNS lookups open them for a moment; a service that listens on UDP in that range, such as WireGuard on 51820, is left out with them. It reads the host's socket tables in `/proc`, which any user may read, and shows no process names: finding them would need rights over every process. With the Linux archive it runs as root only to write the add-on folder, without any capability or network access; its container runs as the image's user |
| `smart` | the health of the disks, read straight from them with no program to install: for each SATA and NVMe disk whether its own SMART check passes, and with their history its temperature, power-on hours, reallocated sectors (SATA), media errors and wear (NVMe). It reads each disk every 30 minutes, as smartd does: a read counts as use of the disk, so reading more often would keep the system from switching an unused disk off. Before each read it asks a SATA disk whether it sleeps, and leaves it asleep if it does; a disk that sleeps at every read for a day is logged once. A SATA disk is also read only when it read or wrote anything since its last read, or when that read is a day old, so a failing check still shows within a day; in between it keeps its last result, so a disk whose own timer switches it off after more than 30 minutes, or that starts its timer again at each SMART command, can still switch off. On Linux the reads and writes are counted in `/sys/block/<disk>/stat`, which the add-on's own commands do not add to (a disk whose counting is switched off in `queue/iostats` is read every time); on Windows by the disk performance counters (`IOCTL_DISK_PERFORMANCE`; with the counters switched off, `diskperf -n`, the disk is read every time). NVMe disks are read every time, so their temperature and hours keep going in the history. A disk that was read before and then cannot be read shows *Cannot be read* in place of its check; the add-on first lists the disks again, so a disk that was unplugged is dropped instead. A SATA disk with SMART switched off, or without SMART, shows *SMART off* in place of its check, without values. A disk that does not tell whether SMART is on and refuses to send its values also shows *SMART off*, unless the same disk (by the serial number the disk itself sends) was read with its values before: then it shows *Cannot be read*, as a failing disk can refuse them too, until it sends its values again or the add-on restarts (while it stays plugged in). Like a disk read with its values, it is then read again only when it was used or its last read is a day old, without listing the disks again. Nothing tells such a refusal from one of a disk whose SMART was switched off on purpose, so after switching SMART off on a disk that does not say so, restart the add-on to see *SMART off*: `sudo systemctl restart den-watcher-smart` on Linux, `Restart-Service UsageControlSmart` in an administrator's PowerShell on Windows. A disk whose SMART values come with a wrong checksum, as some older disks send them, shows only its check. The checks of all disks are one group of extras, *SMART checks*, and their values another, *Disk health*, of which den-watcher keeps 64 values by default: with more disks than that holds (about 21 SATA or 16 NVMe disks), the values of the disks whose serial numbers sort last are left out unless `HISTORY_MAX_ENTRIES` is set higher on the device and its hub, which the add-on logs once; the checks are always kept. A disk the system itself has suspended through runtime power management, as TLP or `powertop --auto-tune` set up on laptops, is woken by the read: an NVMe disk every 30 minutes, an idle SATA disk about once a day, even when nothing else uses it; leave the add-on out where that matters, such as on a laptop that often runs on battery. SAS disks and disks behind RAID controllers are not read, and USB disks are left out on purpose, as some USB adapters reset the disk when they get the commands. Each disk's history is kept under its serial number, so it stays with the disk when names such as `sda` change at a restart. On Linux it runs as root with only the capabilities the disk commands need (`CAP_SYS_RAWIO` for SATA disks, `CAP_SYS_ADMIN` for NVMe disks), read-only access to just those disks, a system call filter, and no network access. `CAP_SYS_ADMIN` allows much more than NVMe commands and systemd cannot grant it only where there are NVMe disks, so it is granted everywhere, with the system call filter keeping it from mounting, loading kernel modules and the like; without NVMe disks, `systemctl edit den-watcher-smart` with `CapabilityBoundingSet=~CAP_SYS_ADMIN` takes it away. On Windows it runs as LocalSystem, since Windows lets only administrators send SMART commands |
| `containers` | the CPU (in percent of the whole machine) and memory of each running Docker or Podman container, with their history, up to 64 containers. Linux with cgroup v2 only (current Raspberry Pi OS, Debian, Ubuntu and Fedora); it reads the kernel's cgroup files, never the Docker socket, which would give it control of the machine. Docker's containers are shown by name, read from `/var/lib/docker/containers`, and those of rootful Podman and CRI-O from their lists in `/var/lib/containers/storage/<driver>-containers/containers.json` (overlay, vfs, btrfs or zfs; with the archive, as rootless Podman keeps its lists below `/home`, which the add-on cannot read), others, such as containerd's, which keeps its names in a database, by their short id; a Docker container that still shows by its short id is logged once, with the path of the settings it looked for. A container shows at the next read after it starts, every 5 seconds: the add-on looks again through all cgroups whenever their number changes or a cgroup comes or goes in the top two levels, where rootful Docker and Podman start theirs (such as `system.slice`), and at least once a minute, so a rootless container, which starts further down below `user.slice`, or a Kubernetes pod with the BestEffort or Burstable class, which starts three levels down below `kubepods.slice`, can take up to a minute to show when another cgroup goes at the same time, as can a container restarted in any Kubernetes pod, whose new cgroup can come in the same read the old one goes; the values of a container stay together under its name when it is made anew, as by an update. Where Docker keeps its data elsewhere, `DOCKER_DIR` names that folder, as `docker info` shows it under *Docker Root Dir* (for the archive in `/etc/den-watcher.env`, then `sudo systemctl restart den-watcher`; one set before with `systemctl edit` is overridden by the settings file's, even by an empty `DOCKER_DIR=` line, so move it there; the archive's service cannot read folders below `/home`, so rootless Docker's names show only with the container). Where the kernel counts no memory per container, as Raspberry Pi OS's does unless `cgroup_enable=memory` is added to `/boot/firmware/cmdline.txt`, it shows only the CPU. It runs as root for those names, but without any capability or network access, and only reads. Not on Windows |
| `processes` | the twenty processes using the most CPU (percent of the whole machine since the previous read) and the twenty holding the most memory (resident, in bytes), live only without history since processes come and go. It reads `/proc/<pid>/stat`, one small file per process (about 1 ms for 100 processes per read). With the Linux archive it runs as root only to write the add-on folder, without any capability or network access, and its container as the image's user; the files it reads every user may read. Where the host mounts `/proc` with `hidepid` (`1` or higher, or `invisible`), it sees only the processes of its own user, without a warning: with the Linux archive root's, in its container none of the host's, as it has no capability to see other users' |
| `bluetooth` | the Bluetooth devices connected to the machine. How many are connected, with its history, and a row per device with its name (the one its owner gave it, else its own) and beside it its battery level where the device tells one, else its kind (headphones, speaker, keyboard, mouse, game controller, phone or computer); a device without a name is named by its kind. It asks BlueZ, the Linux Bluetooth service, over the system D-Bus, and only reads: it starts no scan and connects or disconnects nothing, so devices that are only paired or nearby do not show. A device's address is never shown; its row is kept by a checksum of it. Where BlueZ cannot be asked, as when it is not running, or when the D-Bus rules of the system let only the `bluetooth` group ask it, it shows only how many connections the kernel lists in `/sys/class/bluetooth`, without names; a device connected for audio and calls can count twice there. A machine without a Bluetooth adapter shows nothing. Device names often carry their owner's name, such as *Anna's AirPods*, and show on the page like the rest. With the Linux archive it runs as a throwaway user without privileges, as root on the system D-Bus could have systemd act for it, and writes its report to a folder of its own in the add-on folder, which a link points den-watcher at; where only the `bluetooth` group may ask BlueZ, add `SupplementaryGroups=bluetooth` with `sudo systemctl edit den-watcher-bluetooth`. Its container mounts the host's `/run/dbus` and `/sys` read-only and runs as the image's user, without capabilities or network; there, add the host's `bluetooth` group id with `group_add` in a `compose.override.yaml`. On Windows it asks Windows' own Bluetooth API (`bluetoothapis.dll`) for the paired classic devices, such as headsets, speakers and older keyboards and mice, and Windows' device query (`cfgmgr32.dll`, Windows 10 1809 or newer) for the paired Bluetooth Low Energy ones, such as current game controllers, mice and keyboards, and whether they are connected, without searching for others. Windows reports no battery levels through either. |

Add-ons write what they read to `/run/den-watcher-addons`, which den-watcher shows as [extras](data.md#extras). A hub shows and keeps them like any other extras; a hub from before extras ignores them. An add-on that finds no add-on folder when it starts stops with an error, so its service starts it again a few seconds later; one that cannot read a file for another reason than that the file is missing, such as a file only root may read, logs that once and leaves its values out. The archive's add-on services can open no disk, input or other device but those they read: the smart add-on its disks, read-only, the power and gpu add-ons NVIDIA's devices for `nvidia-smi` and the power add-on the Raspberry Pi firmware's `/dev/vcio` (or `/dev/vchiq`) for `vcgencmd`, the others none. Nor can they open a socket, which as root would let them reach services such as Docker or systemd: the power and gpu add-ons only Unix sockets, for `nvidia-smi`, with Docker's, containerd's, systemd's and D-Bus's hidden from them. The Bluetooth and Wi-Fi add-ons may open Unix sockets too, for the system D-Bus, but run as a throwaway user rather than root, so Docker's and systemd's sockets refuse them and D-Bus treats them like any other user. On Windows, the installer offers them as boxes ([step 2](#2-add-a-windows-pc)) and they write to `C:\ProgramData\Usage Control\addons`. In Docker, the image carries those that have a container (all but gpu, inodes and smart), and `COMPOSE_PROFILES=cub` in `.env` starts Cub's add-ons that have one (pressure, kernel, Wi-Fi and memory), with others added for Grizzly, such as `COMPOSE_PROFILES=cub,power`, or whole groups, such as `COMPOSE_PROFILES=cub,programs`; a group starts those of its add-ons that have a container. `COMPOSE_PROFILES=power` starts the power add-on as a container of its own next to den-watcher. It runs as root without capabilities or network and writes to an in-memory volume. In a container it reads only RAPL and hwmon: a Raspberry Pi 5's total and NVIDIA GPUs need `vcgencmd` and `nvidia-smi` from the host, so for those, use the Linux archive. `COMPOSE_PROFILES=pressure` (or `power,pressure` for both) starts the pressure add-on as a container too, reading the host's `/proc`, mounted read-only at `/host/proc`; it needs no root and runs as the image's user, like den-watcher. It works in a container as it does outside one. `COMPOSE_PROFILES=kernel` (or `power,kernel`) starts the kernel add-on as a container too; it reads the host's `/proc`, mounted read-only, and its network values from `/host/proc/1/net`, the host's own network rather than the container's. It needs no root and runs as the image's user, like den-watcher. `COMPOSE_PROFILES=wifi` starts the Wi-Fi add-on as a container too; it reads the host's `/proc/1/net/wireless` from the mounted `/proc`, so it sees the host's Wi-Fi without network of its own, and asks NetworkManager for the networks nearby through the host's system D-Bus, from the host's `/run/dbus` mounted read-only. As that file is readable by anyone and NetworkManager lets any user read its access points, it runs as the image's user, like den-watcher. `COMPOSE_PROFILES=memory` (or `power,memory` for both) starts the memory add-on as a container too, reading the host's `/proc` read-only; it needs no root and runs as the image's user, like den-watcher. `COMPOSE_PROFILES=ports` starts the ports add-on as a container too; it reads the host's ports from the host's `/proc`, mounted read-only, and needs no root, so it runs as the image's user, like den-watcher. Both: `COMPOSE_PROFILES=power,ports`. `COMPOSE_PROFILES=containers` starts the containers add-on, which mounts the host's `/sys/fs/cgroup` and the `containers` folder in Docker's data folder read-only: `/var/lib/docker/containers`, or below `DOCKER_DIR` in `.env`. Compose does not create that folder where it is missing, so where there is none, as with Podman, the add-on does not start; use the Linux archive there. It runs as root inside its container, so it may read the containers' names, but without capabilities or network, never with the Docker socket. Several add-ons go comma-separated, such as `COMPOSE_PROFILES=power,containers`. `COMPOSE_PROFILES=processes` starts the processes add-on as a container too; it reads the host's processes from its `/proc`, mounted read-only, and needs no root, so it runs as the image's user, like den-watcher. `COMPOSE_PROFILES=bluetooth` starts the Bluetooth add-on as a container too; it asks BlueZ through the host's system D-Bus, from the host's `/run/dbus` mounted read-only, and counts the host's connections in its `/sys` where it cannot. BlueZ lets any user read its devices, so it runs as the image's user, like den-watcher, without capabilities or network. The gpu add-on has no container, since the image carries no `nvidia-smi`; use the Linux archive for it. The inodes add-on has no container: to ask the host's filesystems for their inodes, the container would need the host's whole filesystem mounted, readable as root, which is more than it is worth, so it comes only with the Linux archive. The smart add-on has no container: it would need the host's raw disks and capabilities to send them commands, which the containers here never get, so for it, use the Linux archive.

## 2. Add a Windows PC

Docker on Windows would measure its Linux VM, not the PC, so Windows gets an installer. From the [releases page](https://github.com/Programmer-Den/den-watcher/releases), download `den-watcher-<version>-x64.msi` for most PCs, or `-arm64.msi` for Windows on ARM, and run it. The installers are not code-signed, so SmartScreen warns before it runs.

The setup wizard asks what the PC should do:

- **Only collect this PC's usage for a hub** (preselected): the website is off (`DATA_ONLY=true`), and the PC only answers the hub's requests and keeps no history of its own, only the last 24 hours for a hub that cannot reach it, until the hub has them
- **Collect and also show the website on this PC**: the PC also shows the page and keeps its own history in `C:\ProgramData\Usage Control`

To switch later, install a newer version and pick the other one; the installer of the version that is already installed only offers to repair or remove it. To switch without a newer version, repair the installed version with the option, from a command prompt run as administrator, with the installer of the installed version (`-x64.msi` or `-arm64.msi` as installed), which keeps the other options and restarts the service:

```bat
msiexec /i den-watcher-<version>-x64.msi REINSTALL=ALL REINSTALLMODE=m WEBSITE=1
```

`WEBSITE=0` switches back to only collecting. Either way, the installer:

- installs the program in `C:\Program Files\Den-Watcher` as the Windows service *Den-Watcher*, which starts with Windows and runs under the low-privilege Local Service account
- opens port 9393 in the Windows firewall, for **private networks only**. If Windows set up the network as public, switch it to private in the Windows settings, or the hub cannot reach the PC
- adds the tray icon described below, which starts for everyone who logs in

With the website on, the next page, **Router**, asks whether this PC, as the hub, should also show the router (see [Show the router](#5-show-the-router)): how to read it, its address and the name it gets on the page. It asks for a user and password only for FRITZ!Box, ASUS and SNMPv3, and for the community only for SNMP v2c; UPnP needs no login. An update offers to keep the routers set before. A silent install takes `HUB_ROUTERS` and `ROUTER_PASSWORDS`, such as `HUB_ROUTERS=Box=fritzbox:monitor@192.168.178.1 ROUTER_PASSWORDS=Box=<password>`.

The next page, **Edition**, picks Cub or Grizzly (see [Add-ons](#add-ons)), and lists what Cub collects: the kernel, memory, pressure and Wi-Fi add-ons. Cub installs those and asks nothing more. The Den-Watcher service starts the add-ons, in its Local Service account, through a second `den-watcher.exe` it starts as its child process, the add-on host, so Task Manager groups them under `den-watcher.exe` and they stop and start with the service; the one exception is the smart add-on, which needs more rights and runs as a service of its own. For Grizzly, the page after it, **Which data do you want to collect?**, has the groups of [Add-ons](#add-ons), each with a box, and below it a box for each of its add-ons that work on Windows and for what they collect: under Network, *Networks nearby* (`WIFI_NEARBY`) and below it *Scan every 5 minutes* (`WIFI_SCAN`) under the Wi-Fi add-on; under Bluetooth, *Device names* (`BLUETOOTH_NAMES`). A box is greyed out while one above it is cleared, and pointing at a box tells what it reads. On a first install Cub's choices are ticked; an update starts at Grizzly with the boxes as installed before when one of Grizzly's add-ons is installed or one of Cub's is not. A silent install still picks the add-ons by their options, such as `KERNEL=1`. The **power add-on** (`POWER=1` when installing silently), ticked, installs `den-watcher-power.exe`, which reads what Windows itself offers: the *Energy Meter* performance counters, which Windows 10 and 11 fill where the CPU or firmware has energy meters (Intel CPUs' RAPL counters per package, cores and memory, named as on Linux, and the meters of many laptops and Surface devices), and, on a laptop running on its battery, the power the battery gives, which is what the whole laptop draws (while it is plugged in, Windows only tells how fast the battery charges, so then there is no value). It also reads NVIDIA graphics cards through `nvidia-smi`. Where none of these exist, the add-on shows nothing. The **gpu add-on** (`GPU=1`) installs `den-watcher-gpu.exe`, which reads the fan, clocks, video encoder and decoder, performance state and power limit of an NVIDIA graphics card. The **pressure add-on** (`PRESSURE=1`) installs `den-watcher-pressure.exe`, which reads from the performance counters built into Windows how many threads wait for a processor, how many pages are read from disk for memory and how busy the disks are; Windows has no stall measurement like Linux's, so these are approximations. The **kernel add-on** (`KERNEL=1`) installs `den-watcher-kernel.exe`, which reads what Windows is busy with: context switches and interrupts per second, open handles, established TCP connections and TCP retransmissions per second. It shows handles where Linux shows open files, and it leaves out new processes and sockets, which Windows does not count. The **Wi-Fi add-on** (`WIFI=1`) installs `den-watcher-wifi.exe`, which reads the signal quality and strength of each connected Wi-Fi adapter, and the Wi-Fi networks nearby, through the WLAN API built into Windows. The **memory add-on** (`MEMORY=1`) installs `den-watcher-memory.exe`, which reads the Memory performance counters Windows keeps for Performance Monitor. The **ports add-on** (`PORTS=1`) installs `den-watcher-ports.exe`, which lists the TCP and UDP ports the PC listens on from the tables Windows keeps. The **smart add-on** (`SMART=1`) installs `den-watcher-smart.exe` as the service *Den-Watcher smart add-on*, which reads the disks' health like on Linux, through what Windows itself offers: the NVMe driver's health log for NVMe disks, and the disk drivers' SMART commands for SATA disks. Before each read it asks Windows whether it has switched the disk off, and a SATA disk also itself whether it sleeps, through ATA pass-through where the driver passes ATA commands; it skips a SATA disk Windows' disk performance counters show no reads or writes for since its last read, unless that read is a day old. Windows lets only administrators send these, so unlike the other add-ons it runs as *LocalSystem*; it only sends commands that read. As the Local Service account may change the add-on folder, the add-ons write nothing while that folder, or one above it, is a junction or link, and likewise on a subst or network drive or a volume without a drive letter, which the check cannot tell from one; they write only through the folder they opened and checked, so the smart add-on cannot be sent to write elsewhere, not even by swapping a folder for a junction while it writes. Disks behind RAID drivers such as Intel RST, and NVMe disks with a vendor's own driver instead of Windows' one, may report nothing. The **Bluetooth add-on** (`BLUETOOTH=1`) installs `den-watcher-bluetooth.exe`, which lists the classic Bluetooth devices connected to the PC, such as headsets and speakers, through the Bluetooth API built into Windows (see [Add-ons](#add-ons)). The **processes add-on** (`PROCESSES=1`) installs `den-watcher-processes.exe`, which lists the twenty processes using the most CPU and memory; it asks Windows for all processes in one call, which sees every process, also those of other users and of the system. Installing a newer version with a box cleared removes that add-on. To add or remove one without a newer version, repair the installed version with the add-on's option, like `WEBSITE` above, which keeps the other options and add-ons:

```bat
msiexec /i den-watcher-<version>-x64.msi REINSTALL=ALL REINSTALLMODE=m POWER=1
```

`POWER=0` removes it again. An add-on option takes only `0` or `1`; the installer refuses any other value, also a remembered one, and names the command that gives it. A repair without an add-on option, also one from the wizard, keeps the add-ons as they are. See [Add-ons](#add-ons).

### The tray icon

The bear in the taskbar's notification area shows whether Den-Watcher runs:

| Dot | Meaning |
| --- | --- |
| green | the service runs and answers |
| red | the service is stopped, or runs but does not answer |
| grey | paused from the icon, or starting or stopping |

Its menu, opened with a click:

- **Address** shows where other devices reach this PC, such as `192.168.1.23:9393`: the IPv4 address of the network adapter Windows uses for its default route (else the first private one) and the installer's port, looked up again every minute. This is the address to add on the hub's *Devices* dialog
- **Pairing code for the hub** shows the code the hub's *Devices* dialog asks for when this PC is added there (see [Add the devices on the hub](#4-add-the-devices-on-the-hub))
- **Open hub (address)** opens the page of the hub that collects from this PC, at the address it names. The hub tells the PC its address each time it asks for the usage, so this needs no setup; until a hub has asked, the entry is greyed out. Any device on the local network could claim to be the hub, so check the address before opening it
- **Open the page on this PC** appears when the PC shows the website itself (`WEBSITE=1`)
- **Pause** stops collecting until **Resume**. The service starts again with Windows
- **Stop and exit** stops the service and closes the icon until the next login. The service starts again with Windows
- **Start** appears when the service was stopped some other way

Every logged-in user may start and stop the service from the icon, without an administrator prompt; nothing else about the service changes. The menu follows the Windows display language (English, German, French or Spanish). The setup wizard's last page shows the icon right away; after a silent install it appears at the next login.

To change the other defaults, or to install without the wizard (`/qn`), install from a command prompt run as administrator and add options:

```bat
msiexec /i den-watcher-<version>-x64.msi PORT=8090 WEBSITE=1 RETENTION_DAYS=90
```

| Option | Meaning |
| --- | --- |
| `PORT` | port the PC is reachable on (default 9393) |
| `WEBSITE` | the wizard's choice: `1` to show the website on this PC too and keep its history in `C:\ProgramData\Usage Control`, which uninstalling keeps unless asked to delete it (`DELETE_HISTORY`); `0` to only collect (default `0`) |
| `DEVICE_NAME` | how this PC names itself: on its page with `WEBSITE=1` (default *Host Hub*), and as the name a hub offers when the PC is added from its browser (default: the PC's name), so it counts without `WEBSITE=1` too |
| `HUB_DEVICES` | with `WEBSITE=1`, other devices this PC collects from |
| `HUB_CHECKS` | with `WEBSITE=1`, things this PC checks for whether they answer; see [Check other things on the network](#6-check-other-things-on-the-network) |
| `RETENTION_DAYS` | with `WEBSITE=1`, days of history to keep (default 30) |
| `HISTORY_MAX_ENTRIES` | with `WEBSITE=1`, how many disks, sensors, network cards and GPUs each the history keeps per device (default 64) |
| `BUFFER_HOURS` | without `WEBSITE=1`, hours of usage kept for a hub that cannot reach this PC, from 1 to 168 (default 24) |
| `ALLOWED_HOSTS` | other names this PC answers to, such as a name from the router's DNS the hub uses for it; a name with letters such as ü in its `xn--` form, such as `xn--kche-0ra.lan` for `küche.lan` |
| `DISK_PATHS` | drives or folders whose disks are shown, comma-separated, such as `C:\,D:\` (default: the system drive). Each must exist (a network drive that does not answer is left out until it does): while one cannot be read, the service does not start and names it in the event log, trying again after 10 seconds and then less often, up to every 5 minutes, until an update or repair with a corrected `DISK_PATHS` |
| `UPDATE_CHECK` | with `WEBSITE=1`, `false` stops the daily check for a newer release (default `true`); the installer refuses a value the service cannot read (it takes `true`, `false`, `1`, `0`, `t`, `f` and their upper-case forms, without spaces around), in a repair too, and then names the command that fixes it: for the version that is installed a repair, `msiexec /i den-watcher-<version>-x64.msi REINSTALL=ALL REINSTALLMODE=m UPDATE_CHECK=true`, as `msiexec /i` with only the option does nothing there |
| `WIFI_SCAN` | with `WIFI=1`, `0` stops the Wi-Fi add-on from asking Windows for a scan of the networks nearby every 5 minutes on each connected adapter, as such a scan takes the Wi-Fi to other channels for a moment and can add a short delay; the networks then come only from the scans Windows makes on its own, which while connected are seldom (default `1`); the installer refuses any other value than `0` and `1` |
| `WIFI_NEARBY` | with `WIFI=1`, `0` reads only the connected adapters' quality and signal, not the networks nearby, which are then neither read nor scanned for (default `1`); the installer refuses any other value than `0` and `1` |
| `BLUETOOTH_NAMES` | with `BLUETOOTH=1`, `0` shows each connected device by its kind, such as *Headphones*, instead of its name, which often carries its owner's name (default `1`); the installer refuses any other value than `0` and `1` |
| `RESET_PASSWORD` | with `WEBSITE=1`, `true` deletes the password for changing devices when the service starts; only from an administrator, and the one option that is not remembered, see [the password](#4-add-the-devices-on-the-hub) |
| `DELETE_HISTORY` | with `msiexec /x`, `1` also deletes the history; without it uninstalling keeps it, so installing again shows it again |
| `DELETE_ROUTER_PASSWORDS` | with `msiexec /x`, `0` keeps the encrypted router passwords; by default uninstalling deletes them. The add-on reports are always deleted. The installer's Remove page (run the installer again and pick **Remove**) asks for both with a box each; Windows' own **Uninstall** button in Apps shows no page, so it keeps the history and deletes the passwords |

An update or a repair, such as one from the wizard, closes the tray icon; it comes back at the next login, or right away when the update or repair ran through the wizard. A repair with `REINSTALLMODE=m`, as above, only rewrites the settings and leaves it running, unless it adds or removes an add-on: then it also checks the files, to copy or delete the add-on's program, and closes it too. An update keeps the options it was installed with, except `RESET_PASSWORD`, so double-clicking a newer installer is enough; options given to the update replace the old ones. An option given empty, such as `DISK_PATHS=""`, counts as not given and keeps the remembered value. To clear a remembered `PORT`, `DEVICE_NAME`, `HUB_DEVICES`, `RETENTION_DAYS`, `HISTORY_MAX_ENTRIES`, `BUFFER_HOURS`, `ALLOWED_HOSTS`, `DISK_PATHS`, `UPDATE_CHECK` or `WIFI_SCAN`, give it a single space, such as `DISK_PATHS=" "`, which means its default. `WEBSITE` and the add-on options take a value instead: `WEBSITE=0`, `POWER=0` and so on. The options are remembered under `HKLM\SOFTWARE\Usage Control`. An installer of an older bugfix of the same version, such as `1.2.3a` over `1.2.3b`, refuses to install; Windows Installer itself compares only the numbers before the letters.

The service writes its warnings and errors to the Windows event log (*Application*, source *UsageControl*), and each add-on writes its own there too, under its service's name, such as *UsageControlSmart*. When it cannot serve, for example because another program holds the port right after a reboot, it keeps running and tries again after 10 seconds, then less and less often, up to every 5 minutes; the event log gets the failure once, and again only when it changes or comes back after the service ran for at least 10 seconds. An add-on does the same when its folder is missing.

Builds of `main` are also available, as artifacts of the *Windows installer* workflow runs (pull requests only build the installers when they change the installer, the Go dependencies, a program's command or the add-on and service code, not every change to the backend). Their installers are named after the commit, such as `den-watcher-dev-1a2b3c4-x64.msi`, and numbered `0.0.<run>` inside, which counts as older than any release, so they only install on a PC without a release. The program in them calls itself `dev-<commit>` and does not check for newer releases.

## 3. Add another Linux machine

Install it as in [step 1](#1-set-up-the-hub-with-docker) or [without Docker](#or-set-up-a-linux-machine-without-docker). If it should only report to the hub, turn its own website and history off in `.env` (Docker) or `/etc/den-watcher.env` (service):

```bash
DATA_ONLY=true
```

Leaving its website on does no harm: the hub only reads its usage, and the machine then also keeps its own history and page.

## 4. Add the devices on the hub

On the hub's page, click *Devices*, then add each device with a name and its address and port, such as *Office PC* at `192.168.1.30:9393`. The hub checks that a den-watcher answers there before it adds the device, and starts collecting right away, with no restart. Each address and port can be added only once; the same IP address with another port counts as another device.

Each device has a pairing code, such as `7KQM-X2RP`, which the dialog asks for too, so a hub collects a device's usage only once someone who can see the device gave it the code. The device shows it:

- **with its own website:** on its page, at the bottom of its *Devices* dialog
- **on Windows, data only:** in the [tray icon](#the-tray-icon)'s menu, *Pairing code for the hub*
- **on Linux, data only:** in its log at every start (`docker compose logs den-watcher` or `journalctl -u den-watcher`), and with `docker compose exec den-watcher /den-watcher pairing-code` (Docker) or `den-watcher pairing-code` on the machine (service)

The code is made once, at random, and stays the same. A hub without it, or with a wrong one, still sees that the device answers, so it keeps the device's availability, but gets none of its usage or history: the device shows *waits for its pairing code* in the list, where the code can be entered later, for devices from `HUB_DEVICES` too, and its page says so above the *Availability* card. Once it has the code, the hub fetches what the device kept before, as for a new device. A device on a version without pairing asks for no code; leave the field empty. A device updated from such a version keeps answering the hubs that already collect from it without a code: the ones a data-only device has kept minutes for, and up to 16 hubs that ask in its first 10 minutes after the update. The code keeps a hub from collecting without the device's owner knowing; it is no lock on the data, as a device's own page shows its usage to anyone on the local network anyway.

Pick what each device is:

- *Server / IoT* for a device that should run all the time, such as a NAS or a Pi. When it does not answer, that is an outage, and its card is called *Availability*.
- *PC / laptop* for a device that is switched off when it is not used. The time it is off is not an outage: its card is called *Usage* and shows how much of the time it was on, and its button gets a grey dot instead of a red one while it is off.
- *Phone* for an Android phone running the Den-Watcher app (see [Add an Android phone](#add-an-android-phone)). It has no address, as the phone sends its usage to the hub itself whenever it is on the home Wi-Fi, so the dialog asks only for the name and the pairing code the app shows, and shows a QR code with the hub's address for the app to scan. The dialog draws it only when the page was opened by the hub's address on the network, not on the hub itself as `localhost`, which the phone cannot reach. The time it is away or asleep is not an outage, as for a PC. A phone stays a phone, so the list offers no other kind for it, and its page has no *CPU* card, as Android lets no app read the processor's usage.

The kind can be changed later in the list, for devices from `HUB_DEVICES` too; that asks for the password as well. Devices added before there were kinds, and the ones in `HUB_DEVICES`, are servers until changed.

Opened from a device that is not added yet, the dialog fills in that device's address with port 9393, its kind (a PC when it has a battery or runs Windows), and its name when the hub can find it out: the `DEVICE_NAME` or hostname that its den-watcher reports, or else the name the router gives it in the local DNS. So the quickest way to add a PC is to open the hub's page on that PC. Change the port if the device listens on another one.

The first device you add asks you to choose a password, at least 8 characters, typed twice. From then on, adding or removing a device or changing its kind asks for it; it cannot be changed on the page. If it is forgotten, set `RESET_PASSWORD=true` on the hub, restart it, and unset it again right away: while it is set, every restart deletes the password, and whoever next adds or removes a device chooses the new one. On a Windows hub, repair the installed version with the option, from a command prompt run as administrator (from any other account the option is ignored), then repair it once more without the option. Use the installer of the installed version, `-x64.msi` or `-arm64.msi` as installed; each repair only rewrites the service's settings, keeps the other options and restarts the service:

```bat
msiexec /i den-watcher-<version>-x64.msi REINSTALL=ALL REINSTALLMODE=m RESET_PASSWORD=true
msiexec /i den-watcher-<version>-x64.msi REINSTALL=ALL REINSTALLMODE=m
```

**Download backup** at the bottom of the dialog saves a copy of the hub's database, with the history and the devices, after asking for the password; see [Backups](database.md#backups).

Removing a device deletes its history, availability and kind too, and its alerts, reboots and updates, unless *Keep its history* is ticked; adding a device with the same name within `RETENTION_DAYS` then continues them, and the *since* date of its availability moves on by the time it was removed. The history is kept under the device's name, so renaming a device (removing it and adding it under a new name) starts a new history.

Instead of the dialog, devices can be listed on the hub in `HUB_DEVICES`, each as `name=address:port`, separated by commas. They show as *Set in .env* and are removed only there:

```bash
HUB_DEVICES=Living room Pi=192.168.1.20:9393,Office PC=192.168.1.30:9393
```

Give the devices fixed addresses, for example with an address reservation in the router, since the hub reaches them by the address it was given. A host name works too, as long as it resolves to an address on the local network. The device must then answer to that name: a `.local` name always works, and so does its hostname outside Docker; inside Docker the hostname is the container's, so the machine's bare hostname, like any other name, needs the device's `ALLOWED_HOSTS` (see [Open the page by name](#open-the-page-by-name)). Adding a device by a name it does not answer to says so in the dialog.

Buttons above the dashboard switch between the devices. A dot on each shows whether it answers (green) or not (red, with the time it stopped answering on hover). `DEVICE_NAME` sets how the page names the hub itself (default *Host Hub*).

### Add an Android phone

An Android phone, version 8.0 or newer, sends its data to the hub with the Den-Watcher app. Under *Which data do you want to collect?* the app offers the same groups as the [installers](#add-ons), each with a switch and the data it holds below it: *System basics* (the battery's charge and temperature, the memory used, the storage used) and *Network* (the traffic of Wi-Fi and mobile data, the Wi-Fi networks nearby). All are on at first; what is switched off is neither read nor sent, and the hub's page leaves it out, as it does for data a phone cannot read. While the hub locks the phone (see below), the choice is locked too, as switching everything off would stop recording. The app records the battery's charge and temperature, the memory and storage used, and the traffic of Wi-Fi and mobile data, twice a minute, also while the screen is off: it wakes the phone for each reading and sends it at once. When Android lets the phone sleep deeper, as when it lies still with the screen off for a while or overnight, Android wakes the app only about every 9 minutes, or less often, so the hub shows the phone as not in use then. Android lets no app read how busy the processor is, so a phone has no *CPU* card. The app keeps up to a week's worth of what it recorded (its newest 20,160 readings, longer when it slept) and sends it to the hub whenever the phone is on a network without a data limit, such as the home Wi-Fi, so the hub has the phone's history for the time it was away too. The phone sends nothing over mobile data and nothing anywhere but the hub's address. It tries that address on any network without a data limit, so on another Wi-Fi a device that happens to have the same address and port would get the phone's usage and its pairing code; the code only lets it send made-up readings for the phone from inside your home network. The app remembers the network it first reached the hub on, by its address range and router, as the Wi-Fi's name would need the location permission; when the hub answers on another one, the app says so in a notification and at the top of its screen. If that is your hub, as on a second Wi-Fi at home, tap *It's my network too*. Scanning another hub's code starts over with the network that hub is reached on. While the phone is away or asleep, the hub counts that as time it was not in use, as for a PC that is switched off, and raises no alerts.

1. Download `den-watcher-<version>-android.apk` from a [release](https://github.com/Programmer-Den/den-watcher/releases) on the phone and open it. Android asks once to allow installing apps from the browser or file manager.
2. Open the app. It shows the phone's pairing code, such as `7KQM-X2RP`.
3. On the hub's page, opened from a PC or another phone by the hub's address on the network, open *Devices*, pick *Phone*, enter a name and the code, and click *Add*. The dialog shows a QR code with the hub's address, such as `192.168.1.20:9393`.
4. In the app, tap *Scan hub code*, allow the camera once, and point it at that QR code. The app takes only the hub's address from it, and has no field to type one in. Recording starts, with a notification that Android requires for an app that keeps running. Within half a minute the phone shows on the hub's page.

Once the hub's code is scanned, *Open the hub's page* in the app opens the hub's page in the browser. Recording starts again by itself when the phone restarts. Once the hub took the phone's usage, the app locks the hub's address and *Stop recording*, so whoever has the phone cannot move it to another hub or stop it quietly. To change either, click *Allow changing the hub* for the phone under *Devices* on the hub's page: within half a minute, while the phone is on the home network, the app lets you scan another hub's code or stop recording, for 10 minutes from the click. The app takes this only from the hub it was set up with: with its first push the hub gives it a key of its own, which the app never shows, and proves each allowed change with it, so another server set up at the hub's address cannot unlock the app. The hub gives a phone its key only once, and again only within the 10 minutes after *Allow changing the hub*. The lock is in the app only: Android always lets the phone's user force-stop the app, clear its data or uninstall it, and the hub then shows the phone as not in use, the same as when it is away. Some phone makers stop apps in the background to save battery; if the hub misses hours, tap *Battery settings* in the app and let Den-Watcher run without restrictions. An app that was installed anew has a new code: remove the phone in the *Devices* list with *Keep its history* ticked, and add it again under the same name with the new code.

**Wi-Fi networks nearby**: under *Wi-Fi networks nearby*, tap *Allow*, and then *Allow all the time*, which Android 11 and later ask for in the app's settings (*Location > Allow all the time*). The app then also records the Wi-Fi networks Android saw nearby, each access point under a hash of its hardware address, with its signal, channel and security, as the Wi-Fi add-on of a PC does, so the phone shows under *Compare devices*, *Wi-Fi nearby*. Android gives them only with the location permission, which is why it asks for it: the app never reads the phone's position and starts no scan, it reads only what Android scanned on its own, which a phone with its screen off does seldom. Only while the app is open, it reads them only then. It keeps them, also from while the phone is away, until the phone is on the home Wi-Fi again, up to its newest 20,160 scans, and sends them in the hour they were seen, so the hub can tell where the phone was. Without the permission it reads none.

Before you put the app on a phone someone else uses, read [Intended use](../README.md#intended-use): the times the phone was at home and in use tell a lot about that person.

## 5. Show the router

The hub can show your router as a device of its own, with its availability and charts, even though the router cannot run den-watcher: the hub asks the router itself, over the local network.

- **Any router with UPnP** (ASUS, Technicolor, FRITZ!Box and most boxes of internet providers): the internet traffic, the speed of the line and whether the connection is up, without a login. Switch on UPnP in the router's settings.
- **ASUS with its login**: also the CPU per core, memory, traffic per port and Wi-Fi band, the clients online, each by name with how it is connected (on a cable, or the Wi-Fi band), and the temperatures of the CPU and the radios, through the router's web interface, read as the ASUS app reads it. It logs in once and keeps the token; some models then sign the admin out of the web interface, so log in there again if that happens. It is read every 30 seconds, to spare the router's CPU. Best create a user for it in the router, if the model allows one. With **AiMesh**, list only the main router: the hub shows each other router of the mesh (each node) as a device of its own, named as in the main router's settings (with " (AiMesh)" added where another device has that name). It shows whether the node is online, so a node that drops out is an outage and, after 2 minutes, an alert, and how it is linked to the mesh (by cable, or the Wi-Fi band with the link's signal in dBm), how many devices are connected to it, its model, firmware and address. All of that comes from the main router (its `get_cfg_clientlist`), so a node needs no login of its own and is not asked itself. A node that joins the mesh shows within a minute (within 10 minutes when the mesh had no other node, as a router without nodes is asked for them only that often, to spare it); one that is missing from the main router's list for an hour is no longer shown, with its history kept. Where a device with the Wi-Fi add-on hears the mesh, *Wi-Fi nearby* under *Compare devices* names its access points after the main router and the nodes instead of numbering them.
- **FRITZ!Box with a FRITZ!Box user**: the internet traffic, the speed the line synchronized at, the noise margin of a DSL line, the uptime and the clients online, each by name with how it is connected (the LAN port of a cable, Wi-Fi, or the guest network), over TR-064, the FRITZ!Box's interface for applications. Allow it under *Home Network > Network > Network Settings > Allow access for applications*, and create a user for it under *System > FRITZ!Box Users*. It is read every 30 seconds. A wrong password is not tried again for 5 minutes, as the FRITZ!Box blocks logins for a while after wrong ones.
- **SNMP** (MikroTik, OpenWrt with `snmpd`, Ubiquiti, business routers and switches): the traffic, errors and speed of every port that is up, and where the router tells them the CPU per core, memory and uptime. SNMPv2c needs the community (`public` unless it was changed); SNMPv3 a user with authentication (SHA) and encryption (AES-128), whose password is used for both. Switch on SNMP in the router's settings, read-only.

A login is asked for only for a router that needs one: none for UPnP, the community for SNMPv2c, a user and password for ASUS, FRITZ!Box and SNMPv3.

**Privacy:** Read from the router over the local network only. No data is sent to any server; everything stays on your own devices, and a router password is stored encrypted where the system allows it. The hub only reads: it never changes a setting of the router. The installers show this before they ask for the router.

Set it up:

- **Docker:** run `sudo ./setup-router.sh` next to `compose.yaml`, then `docker compose up -d`. It asks for the router and writes `HUB_ROUTERS` to `.env`; a router's password, or an SNMP community other than `public`, goes to `router-secrets/router-passwords`, which only root and the container's user can read. Docker has no key store to encrypt it with, so it is protected by the file's owner and permissions.
- **Linux service:** `sudo ./install.sh`, run in a terminal, asks for the router after the add-ons, also on an update, where it can also stop showing it. With `--addons=…` it does not ask for the router and keeps it as it was, so run it without the option to set the router up or change it. A router's password or SNMP community is encrypted with `systemd-creds` with the machine's own key (and its TPM, where there is one), so the file `/etc/den-watcher-router-passwords.cred` is of no use on another machine; systemd decrypts it only for the service. Before systemd 250, which cannot encrypt, it is stored readable by root only. `--uninstall --purge` deletes it.
- **Windows, with the website on:** the installer's **Router** page (see [Add a Windows PC](#2-add-a-windows-pc)). It hands the password to the service through a registry key only the system, administrators and the Local Service account can read; at its next start the service encrypts it with DPAPI for that account into `C:\ProgramData\Usage Control\router-passwords.dpapi`, which only programs running as Local Service on this PC can decrypt (the service, its add-ons and some of Windows' own services), and deletes it from the registry. Leaving the password empty in an update keeps the one stored for that name. A password given to the installer cannot hold a double quote or the two characters `\0`. If a router's setting is wrong, the service runs without the routers and says why in the event log. An update keeps the file; uninstalling deletes it, unless `DELETE_ROUTER_PASSWORDS=0` or its box on the Remove page is cleared.
- **By hand:** list routers in `HUB_ROUTERS`, each as `name=protocol:address`, with the protocol `upnp`, `asus`, `fritzbox`, `snmp` or `snmpv3`, and for a login the user before the address. The passwords, and an SNMP community other than `public`, go in a file named by `ROUTER_PASSWORDS_FILE`, one `name=password` per line:

```bash
HUB_ROUTERS=Router=upnp:192.168.1.1,Office router=asus:admin@192.168.2.1,Box=fritzbox:monitor@192.168.178.1,Switch=snmp:192.168.1.2,Core=snmpv3:monitor@192.168.1.3
```

The router shows as *Router* in the *Devices* dialog and is removed only where it is set. Its page shows only what the router tells: over UPnP the network card (*WAN*) and the internet connection, with an ASUS login the CPU, memory and temperatures too, from a FRITZ!Box the line and the clients, over SNMP every port. A router that does not answer is an outage, as for a server. Routers that pass traffic in hardware (NAT acceleration) may count less traffic than goes through them; the page shows what the router counts.

## 6. Check other things on the network

Things that cannot run den-watcher, such as a printer, a NAS, an IP camera or a smart TV, can still show on the hub as devices of their own: the hub checks every 15 seconds whether each one answers, and how long the answer took. The page shows the response time with its chart, and the time it did not answer as outages in its availability, like any device. A thing that is pinged gets 5 pings per check, 200 milliseconds apart, so the page also shows the packet loss, the share of them that got no answer, and the jitter, how much the response times varied, each with its chart: a Wi-Fi camera that loses pings now and then shows it there before it drops out. It counts as not answering only when none of the 5 is answered. Set a thing that is switched off when not in use, such as a TV, to *PC or laptop* in the *Devices* dialog, so that time counts as not in use instead.

List them in `HUB_CHECKS`, each as `name=address:port` to connect to a TCP port, or `name=address` to ping:

```bash
HUB_CHECKS=Printer=192.168.1.50:631,NAS=192.168.1.10,Camera=192.168.1.60:554
```

- **A port** checks that the service on it runs, not just the machine: the hub opens a connection and closes it right away, without sending anything. A closed port counts as not answering. Common ones: 631 (printers, IPP), 9100 (printers), 445 (Windows shares, NAS), 554 (cameras, RTSP), 80 or 443 (web interfaces), 22 (SSH).
- **A ping** works for anything that answers one, with IPv4 only. It needs no privileges: Windows lets any program ping, and on Linux the system must allow ping sockets for the service's group in `net.ipv4.ping_group_range`, which most distributions (Debian, Raspberry Pi OS, Ubuntu, Fedora) and Docker do; `compose.yaml` sets it for the container too. Where it is not allowed, the device shows as not answering and the log says why; give a port instead.

Only addresses on the local network are checked; a name that resolves elsewhere is refused. On Windows, set it with `HUB_CHECKS` on the command line of the installer, with `WEBSITE=1`. A check shows the address it uses in the *Devices* dialog and is removed only where it is set. A wrong entry leaves out the checks, not this device's own monitoring, and the log says why.

## 7. Show the usage in Grafana

With `PROMETHEUS=true`, the hub, or a single device with its own page, also answers `GET /metrics` with the current usage of itself and of every device it collects from, in the Prometheus text format. Prometheus scrapes it and keeps the values as long as it is set to, and Grafana draws them; both run on your own network, without an account. Without the setting, `/metrics` is not found. A data-only device does not serve it: scrape the hub, which lists that device too.

```bash
PROMETHEUS=true
```

A scrape config for Prometheus, with the hub at `192.168.1.20`:

```yaml
scrape_configs:
  - job_name: den-watcher
    scrape_interval: 15s
    static_configs:
      - targets: ["192.168.1.20:9393"]
```

`/metrics` answers only the local network, and only to the names the page does (see [Open the page by name](#open-the-page-by-name)): a target by IP address works, a name from the router's DNS needs `ALLOWED_HOSTS`. Prometheus in Docker on the same machine reaches it at the machine's LAN address, not at `localhost`. Every value has the labels `device`, the device's name (*Host Hub* for this device without `DEVICE_NAME`), and `id`, its id in `GET /api/devices`. A device that does not answer has `denwatcher_device_up` 0 and no other values but its alerts. The metrics are listed in [The usage for Prometheus](data.md#the-usage-for-prometheus).

On Windows, the installer has no option for it; set it on a Linux hub.

## 8. Check the devices from outside

With `STATUS_ADDR`, the hub also serves the status page: a minimal page on a port of its own that tells whether each device is online, offline or switched off and how many alerts it has, and nothing else: no values, no addresses, no version. It is the only part of den-watcher meant to be reachable from the internet, so you can check on your devices from anywhere. In Docker, set the port on the host in `.env`:

```bash
STATUS_PORT=9443
```

`compose.yaml` then publishes it and sets `STATUS_ADDR=:9443` inside the container; for the Linux service, set `STATUS_ADDR=:9443` in `/etc/den-watcher.env`. Then:

1. Open the hub's page on the local network, click *Devices* and set a password under *Remote status page*. Setting or changing it asks for the password for changing devices; changing it signs everyone out of the status page. Until it is set, the status page shows no devices.
2. Forward the port on the router to the hub, such as TCP 9443 to `192.168.1.20:9443`, and open `https://<your public address>:9443` from outside. With a public address that changes, a dynamic DNS name from the router helps.
3. The page uses HTTPS with a certificate the hub makes itself, so the browser warns the first time. Compare the fingerprint the browser shows with the one in the *Devices* dialog (and in the hub's log) before you continue; if they are the same, the connection goes to your hub. The certificate is kept in the database and replaced 30 days before it ends, after about two years; the browser warns once more then.

How it is protected: it answers only HTTPS (TLS 1.2 or newer), shows nothing but the sign-in form until the password is given, and keeps a visitor signed in for 30 days with a cookie that is sent only over HTTPS and only by the page itself. Each address may send 60 requests a minute; after 5 wrong passwords it may guess no more for 15 minutes, and after 50 wrong passwords from all addresses together within an hour only a browser that signed in before can sign in until the hour is over, so others guessing cannot keep you out, while those signed in keep seeing the page. One address may hold 8 connections at once. Every wrong password is answered one second late. It serves only `/`, `/login` and `/logout`; the website and the API stay on the local network. Choose a long password: it is the only thing between the internet and the list of your devices.

On Windows, the installer has no option for it; set it on a Linux hub.

## Run from source

To run den-watcher on a computer without Docker or an installer, such as a Mac, build the website once and then the binary. You need Node.js (version in `frontend/.nvmrc`) and Go (version in `backend/go.mod`). In PowerShell on Windows:

```powershell
cd frontend; npm ci; npm run build; cd ..
cd backend; go build -o den-watcher.exe ./cmd/den-watcher
$env:DEVICE_NAME = "Office PC"   # optional
.\den-watcher.exe
```

On Linux and macOS, build with `go build -o den-watcher ./cmd/den-watcher` and start it with `DEVICE_NAME="Office PC" ./den-watcher`. The page is then at <http://localhost:9393>, and the history is kept in `usage-control.db` in the folder it was started from. Add `DATA_ONLY=true` to only report to a hub.

On Windows, allow `den-watcher.exe` on private networks when the firewall asks on the first start. Start the built binary rather than `go run`, which builds a new file each time, so the firewall would ask again.

## Settings

Settings are environment variables. In Docker they go in `.env` next to `compose.yaml`; for the Linux service in `/etc/den-watcher.env`; on Windows they are installer options (see [step 2](#2-add-a-windows-pc)). A setting takes effect at the next start. An invalid value stops the program with a message that names the setting.

| Setting | Default | Meaning |
| --- | --- | --- |
| `PORT` | `9393` | Docker only: the port on the host. The container always listens on 9393 inside |
| `IMAGE_TAG` | `latest` | Docker only: `latest`, a release such as `0.1.0`, or `main` |
| `LISTEN_ADDR` | `:9393` | outside Docker: the address and port to listen on, such as `:8090` |
| `PUBLIC_PORT` | the port of `LISTEN_ADDR`; `PORT` in Docker | the port the page is reachable on from the network. A hub sends it to the devices it collects from, so a Windows PC can link to the hub's page |
| `DISK_PATHS` | `/`, or the system drive on Windows | comma-separated paths whose disks are shown; in Docker, mount each one read-only first |
| `DATABASE_PATH` | `usage-control.db` in the working folder; set by Docker, the Linux service and the Windows installer | the SQLite file for the history, or with `DATA_ONLY` for the usage kept for the hub |
| `RETENTION_DAYS` | `30` | days of history to keep, 1 to 3650 |
| `HISTORY_MAX_ENTRIES` | `64` | disks, sensors, network cards and GPUs each that the history keeps per device, and 8 times as many values of extras, 1 to 10000 |
| `HISTORY_FLUSH_MINUTES` | `10` | minutes of history kept in memory before they are written to the database together, 1 to 60; a power cut loses what waits ([Writing](database.md#from-reading-to-chart)) |
| `DEVICE_NAME` | *Host Hub* | how the page names this device |
| `HUB_DEVICES` | none | other devices to collect from, as `name=address:port`, comma-separated |
| `HUB_CHECKS` | none | things that run no den-watcher, such as a printer, to show as devices the hub checks for whether they answer, as `name=address:port` to connect to a TCP port or `name=address` to ping, comma-separated; see [Check other things on the network](#6-check-other-things-on-the-network) |
| `HUB_ROUTERS` | none | routers to show as devices, as `name=upnp:address`, `name=snmp:address`, or `name=asus:user@address`, `name=fritzbox:user@address` or `name=snmpv3:user@address`, comma-separated; see [Show the router](#5-show-the-router) |
| `ROUTER_PASSWORDS_FILE` | `router-passwords` in systemd's credentials folder; set by `compose.yaml`; on Windows, without it, the passwords the installer stored (see [Show the router](#5-show-the-router)) | the file with the passwords of routers that need a login, and SNMP communities other than `public`, one `name=password` per line |
| `DATA_ONLY` | `false` | `true` serves only the usage for a hub, with no website and no history of its own |
| `BUFFER_HOURS` | `24` | with `DATA_ONLY`, hours of usage kept for a hub that cannot reach the device, 1 to 168; see [While the hub is away](architecture.md#while-the-hub-is-away) |
| `RESET_PASSWORD` | `false` | `true` deletes the password for changing devices at start; unset it again right after |
| `UPDATE_CHECK` | `true` | `false` stops the daily check for a newer release. When set, it must be `true` or `false` on every device, data-only ones too, which never check: an invalid value stops the program |
| `ALLOWED_HOSTS` | none | other names this device answers to, comma-separated, besides IP addresses, `localhost`, its hostname and `.local` names. A name with letters such as ü goes in the `xn--` form the browser sends, such as `xn--kche-0ra.lan` for `küche.lan`; written as `küche.lan` it is left out with a warning |
| `STATUS_ADDR` | none | the address of the status page, such as `:9443`, for outside the local network; see [Check the devices from outside](#8-check-the-devices-from-outside). Set by `compose.yaml` from `STATUS_PORT`. Not with `DATA_ONLY`: both together stop the program |
| `STATUS_PORT` | none | Docker only: the port on the host for the status page, which turns it on |
| `STATUS_PUBLIC_PORT` | the port of `STATUS_ADDR`; `STATUS_PORT` in Docker | the port the *Devices* dialog names for the status page |
| `PROMETHEUS` | `false` | `true` serves `GET /metrics`, the usage of this device and of every device it collects from for Prometheus; see [Show the usage in Grafana](#7-show-the-usage-in-grafana). Not with `DATA_ONLY`: both together stop the program |
| `DOCKER_DIR` | `/var/lib/docker` | for the containers add-on: Docker's data folder, as `docker info` shows it under *Docker Root Dir*, from which it reads the containers' names. The Linux service cannot read folders below `/home`, so rootless Docker's names show only with the container. The inodes add-on leaves out the containers' layers mounted below it |
| `WIFI_NEARBY` | `1` | for the Wi-Fi add-on: `0` reads only the connected Wi-Fi interfaces' quality and signal, not the networks nearby, which are then neither read nor, on Windows, scanned for. Takes `0` or `1`; another value is logged and counts as `1`. The Linux service's add-on reads it from `/etc/den-watcher.env`, so restart `den-watcher-wifi` after a change |
| `BLUETOOTH_NAMES` | `1` | for the Bluetooth add-on: `0` shows each connected device by its kind, such as *Headphones*, instead of its name, which often carries its owner's name. Takes `0` or `1`; another value is logged and counts as `1`. The Linux service's add-on reads it from `/etc/den-watcher.env`, so restart `den-watcher-bluetooth` after a change |
| `ADDONS_DIR` | `/run/den-watcher-addons` for the Linux service; else none | the folder add-ons write their values to, which are shown as extras. Fixed for the Linux service, whose add-ons always write to `/run/den-watcher-addons`: leave it out of `/etc/den-watcher.env` |
| `HOST_PROC`, `HOST_SYS` | set by `compose.yaml` | where the host's `/proc` and `/sys` are mounted in a container |
| `HOST_ETC` | set by `compose.yaml` | where the host's `os-release` is mounted in a container, for the System card; without it, the card leaves the system out there |

## Updating

**Docker**, in the folder with `compose.yaml`:

```bash
git pull               # when compose.yaml itself changed
docker compose pull
docker compose up -d
```

**Linux service:** unpack the newer archive and run `sudo ./install.sh` again.

**Windows:** run the newer installer; it keeps its options.

The history and settings stay in every case. What changed is on the [releases page](https://github.com/Programmer-Den/den-watcher/releases). When a new version changes the database layout, it keeps a copy of the old file first ([details](database.md#updates-to-the-layout)), except the update to 3.x: it keeps no copy, so download a backup first (**Download backup** in the devices dialog, see [Backups](database.md#backups)).

On a release, the hub checks GitHub once a day for a newer one (an hour after a failed check), without an account, and the page names it with a link. Nothing is downloaded or installed; updating stays your step. Builds of `main` and data-only devices never check. `UPDATE_CHECK=false` turns it off.

**Port change after 0.1.0:** version 0.1.0 and builds before the change listened on 8080. Existing installs keep their port: a Docker install that set `PORT` in `.env`, a Windows install, which remembers the port it was installed with, and a Linux service with `LISTEN_ADDR` in `/etc/den-watcher.env`. A Docker install that never set `PORT` moves to 9393 after `git pull` and `docker compose up -d`; set `PORT=8080` in `.env` to stay on the old port, or update the address on the hub's *Devices* dialog.

**Moved to Programmer-Den:** the repository moved from Chriszly to the Programmer-Den organization. The old addresses of the repository forward to the new one, so `git pull` and the hub's update check keep working. Two things do not forward:

- **Docker:** new images are published as `ghcr.io/programmer-den/den-watcher`. `ghcr.io/chriszly/den-watcher` keeps the versions it has but gets no new ones. `git pull` brings the new name into `compose.yaml`; then run `docker compose up -d`. A `compose.yaml` or setting of your own that names the image needs the new name too.
- **Demo:** it is at <https://programmer-den.github.io/den-watcher/>; the old address no longer answers.

**Renamed from usage-control after 2.0.7a:** installs of 2.0.7a and older keep their history and settings when they switch to den-watcher. The Docker image under the old name stopped at 3.0.0; the Linux `install.sh` and the Windows installer still take over an old install:

- **Docker:** the image is now `ghcr.io/programmer-den/den-watcher`, and the compose service is called `den-watcher`. Images were published as `ghcr.io/chriszly/usage-control` up to and including version 3.0.0 and no longer are, so an old `compose.yaml` stays on 3.0.0. To go on, `git pull` (the old repository address forwards to the new one), then run `docker compose up -d --remove-orphans`, which pulls the new image and replaces the old container. The history stays in the same volume, and the database file keeps its name, `usage-control.db`.
- **Linux service:** `sudo ./install.sh` from the new archive takes over the old install once. It moves `/etc/usage-control.env` to `/etc/den-watcher.env`, `/var/lib/usage-control` to `/var/lib/den-watcher`, and the router password and `systemctl edit` settings too. The installed add-ons are kept, and the old services and programs are removed. From then on it is `sudo systemctl restart den-watcher`.
- **Windows:** run the new installer over the old one. It replaces the install named Usage Control, and keeps its options, add-ons and history. The services keep their names (`UsageControl`, and `UsageControlSmart` for the smart add-on), and so do the data folder `C:\ProgramData\Usage Control` and the registry key `HKLM\SOFTWARE\Usage Control`.
- **Hub and devices** can be updated in any order: a hub still reads devices that have not been updated yet, and the other way round.
- **Demo:** it moved to <https://programmer-den.github.io/den-watcher/>.

Deploying to the maintainer's Pi lives in the private settings repository rpi-deploy-and-update (its *Deploy to Pi* and *Update Pi* buttons); this repository only builds and publishes the image.

## Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| A device shows a red dot | The hub has had no answer for 20 seconds. Check that the device is on and den-watcher runs on it (`docker compose ps`, `systemctl status den-watcher`, or the *Den-Watcher* service on Windows), and that the address and port on the hub are right |
| A red banner says the Host Hub is not answering, and the other devices have hollow dots | The page lost its connection to the hub, which all values come through, so nothing on it is live. Check that the hub is on and den-watcher runs on it (`docker compose ps` or `systemctl status den-watcher`), and that your phone or PC is still on the same network. The page keeps trying and clears the banner by itself as soon as the hub answers |
| A Windows PC cannot be added or stays red | The network is set to public, so the firewall blocks the port. Switch it to private in the Windows settings |
| "no den-watcher answers at …" when adding | Nothing answered at that address within 4 seconds; the hub's log says why. Open `http://<address>/api/metrics` from the hub's network to check |
| "This address is the hub itself" when adding a VM or container that runs on the hub, reached through a forwarded port such as `<hub's IP>:9394` | The page refuses every address of the hub, whatever the port. List the device in `HUB_DEVICES` instead, which may name the hub's own addresses |
| A device added on the page stays red after an update | Its address is one of the hub's own, such as a VM at `<hub's IP>:9394` or Docker's bridge gateway, which the hub no longer connects to for devices added on the page; its dashboard says so, and the log names the device at the start ("a device added on the page is at an address of the hub itself"). Remove it on the page with its history kept, then list it in `HUB_DEVICES` under the same name, which keeps its history and availability |
| `403 only reachable from the local network` | The request came from outside the local network, or through a proxy. Open the page directly from the LAN. In Docker, check that the port is published as `0.0.0.0:…` (`ss -tlnp` on the host) |
| `421 Misdirected Request` | The page was opened by a name the device does not know. Use the IP address or a `.local` name, or add the name to `ALLOWED_HOSTS` |
| The page stays empty inside another page, such as a Home Assistant iframe card | The page refuses to be shown in a frame of another site, so no other page can lay itself over it; there is no setting to allow it. Open it in its own browser tab instead |
| Temperature shows as unavailable | The system does not report it to programs, as on most Windows PCs and in containers without the host's `/sys` |
| No GPU card | No GPU the system reports without extra rights; see [GPUs](data.md#gpus) |
| The program does not start: "check DISK_PATHS" | A path in `DISK_PATHS` cannot be read; the message says which. In Docker, mount it read-only in `compose.yaml` first; on Windows, list drives or folders that exist, such as `C:\,D:\` |
| The program does not start: "the database was written by a newer version" | An older version was started on a newer database. Start the newer version again, or put the `.backup` copy back ([details](database.md#updates-to-the-layout)). From 3.0.0 on there is no `.backup` copy: only a backup downloaded before the update brings an earlier version back |
| Some disks, sensors or network cards are missing from the charts | The device reports more than `HISTORY_MAX_ENTRIES` (64) of them; the log says so. Raise it on the hub |

Logs: `docker compose logs` for Docker, `journalctl -u den-watcher` for the Linux service, and the Windows event log (*Application*, source *UsageControl*) on Windows.
